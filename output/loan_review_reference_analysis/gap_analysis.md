# Phase 3 — Loan Review gap analysis

Reviewed September 30, 2026. This is an analysis, not an implementation. Existing workflow files and historical workbooks were not changed.

## Conclusion and scope

The current skill is `sec-credit-analysis` in `SKILL.md`; there is no separate Loan Review entry point among the inspected project sources. Its financial tables partially resemble the references, but it does not currently produce a complete historical-style Loan Review. Three sources of behavior disagree: the skill describes an eight-section memo, `references/output-format.md` specifies that memo, and `scripts/credit_memo_writer.py` actually renders three quarterly or four annual financial sections.

The most urgent issues are unsupported values and assertions produced by deterministic code, not just possible LLM hallucinations. Changing the prompt alone would leave zero-filled inputs, debt-service proxies, incomplete LTM values, invented dashboard covenant thresholds and unsupported trend language in place.

Reference basis: all 13 workbooks analyzed in Phase 2, comprising five annual and eight quarterly reports. Report IDs R01–R13, exact archive members, visible-cell anchors and workbook inventories are recorded in `evidence_index.md`. `analysis.md` documents observed conventions and defects; `canonical_template.md` specifies the inferred annual and quarterly formats. Historical mistakes, stale hidden cells and mismatched exhibits are not normative requirements.

Evidence labels below distinguish **runtime** (implemented behavior), **instruction** (directions that may influence an agent but are not necessarily implemented), and **exposure** (a missing safeguard, not proof that a particular generated report contains a fabricated claim). Source locations refer to the inspected version; function names are stable navigation anchors.

## 5. Confirmed local reproductions

Read-only, in-memory probes of `credit_memo_writer.py` used synthetic empty dictionaries and two dated columns. They did not access external services, process real borrower data or change workflow files. This is targeted verification of behavior, not an end-to-end production run.

| Probe | Actual result | Consequence |
|---|---|---|
| Empty quarterly income inputs | “Pre-tax margin was slightly increased to 0.00% … from 0.00%” | The writer invents a numeric margin and direction from missing facts. |
| Empty financial inputs and commentary | “Total revenues increased to $N/AM … mainly driven by [refer to MD&A]” | Missingness is mixed with asserted trend and unresolved placeholder. |
| Empty liquidity inputs | “indicating tightened short-term liquidity” | A negative assessment is produced without ratio evidence. |
| Empty EBITDA/leverage inputs | “LTM EBITDA increased by 0.0%” and “The improved in total leverage to N/A” | Missing values become growth and improvement language. |
| One EBITDA observation of 10 | `_compute_ltm_ebitda` returns 10.0 | No four-quarter completeness requirement in this fallback. |

The dashboard covenant insertion, CapEx debt-service proxy, D&A/inventory defaults and latest-filing selection were confirmed by static inspection. No live BQ/dbt/LLM run was performed; database contents, actual agreement accuracy and a particular production report's factual correctness were not independently verified.

## 6. Missing-information policy

The historical reports show blanks, N/A and omitted/hidden conditional sections, but do not provide a consistent convention for every missing-evidence case. In particular, their repeated no-default and acceptable-risk sentences are assertions, not a missing-data policy. The explicit status rules below are proposed safeguards required by the user, not falsely attributed to all references.

| Evidence state | Required handling |
|---|---|
| Missing field in current borrower package | `Not provided` or a precise unavailable statement; retain core structural slot. |
| Search, covenant test or credit assessment not performed | `Not assessed`; no inferred negative search, compliance or branch conclusion. |
| Verified non-applicability | `N/A`, with concise basis when useful. Do not equate missing agreement with no covenants. |
| Numeric movement supported, explanation absent | Report the movement; state that the supplied materials do not explain it, or omit the causal clause. |
| Insufficient inputs for a calculation | Mark result unavailable and identify missing inputs; no zero defaults or proxies. |
| Conflicting evidence or different definitions | Flag discrepancy/non-comparability; withhold dependent conclusion until resolved. |
| Conditional module known applicable, evidence missing | Brief unavailable status, not a completed fabricated module and not silent concealment. |
| Conditional module verified irrelevant | Omit its detailed content, consistent with the reference form. |

No final report should contain unresolved `[X.XX]`, `[refer to MD&A]`, fictional examples or a reassuring default sentence. Empty signature fields are intentional unsigned fields, not permission to fabricate approvals.

## 7. Required grounding contract and implementation sequence

Maintain two separate input roles:

1. **Reference specification:** section order, permitted conditional modules, typography, table shape, analytical sequence and sentence patterns. No borrower values, explanations, covenant terms, valuations, default findings or credit decisions.
2. **Current borrower evidence:** financial statements/spreads, agreements/amendments, certificates, current rating records, supplied industry/market evidence, management commentary, searches and authorized branch decisions. Each item needs entity, dates, source identity and a locator.

A numerical claim requires either a directly supported fact or a deterministic calculation with complete supported inputs and the applicable definition. A causal claim requires a passage supporting that cause for the same comparison. A risk conclusion requires supported rationale; “the Branch concluded” additionally requires a supplied branch decision. A search result requires an actual search record. These evidence types are not interchangeable.

Recommended implementation order, for a later authorized phase:

1. Remove unsafe numeric defaults, trend assertions, dashboard covenant examples and mandatory unsupported sample conclusions. These are grounding blockers.
2. Define a borrower evidence schema, field-level provenance, explicit missing states, requested review mode and fiscal-period roles. Extend input support beyond SEC-only public companies.
3. Reconcile financial definitions and all dbt/inline/writer paths. Resolve debt ratio, debt service, EBITDA, quick ratio, cash reconciliation and TTM completeness before narrative polish.
4. Replace string-only commentary with supported claims and evidence references; match source periods; treat document instructions as data, never as agent instructions.
5. Implement the canonical annual/quarterly forms and conditional modules. Update skill and format documentation to match executable output.
6. Add final validation before output is considered complete. Existing `verify_marts_in_bq` checks existence/row counts, not claim truth or report fidelity; model JSON conformance is not evidence verification.

Acceptance criteria for that later phase:

- All borrower-specific facts resolve to current-source evidence or valid formulas; historical report content cannot satisfy this requirement.
- Missing inputs produce no invented values, direction, causal explanation, compliance result or credit judgment.
- Periods, units, entity and metric definitions agree across tables, prose and Summary.
- Annual and quarterly order and detail match the inferred reference modes; conditional modules follow applicability and evidence.
- Covenant terms and valuation assumptions cannot come from placeholders or defaults.
- Unknown and conflicting evidence remain visible, and unperformed checks are not represented as completed.
- Final-form visual inspection checks table alignment, wrapping and pagination; automated checks cover unsupported claims, residual placeholders and table/prose contradictions.

Existing strengths to retain: raw XBRL provenance fields, explicit SEC ingestion, common-size columns, annual/quarterly core table variants, YTD intent, two-decimal ratio presentation, and the commentary prompt's explicit instruction not to invent explanations. These are useful foundations, but do not yet enforce the user's grounding requirement end to end.
